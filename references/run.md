# Публикация и восстановление

Подставляй абсолютные пути к scripts/dashboard.py в папке скилла и к каталогу прогона. Скрипт работает на Python 3 со стандартной библиотекой.

Сначала выполни стартовую публикацию и запуск сервера из пункта 2. Для первого снимка используй пустой questions и пустые списки материалов. Сразу после получения URL из stdout отправь ссылку в чат промежуточным сообщением и продолжай шаги с тем же сервером.

1. В notes.md сохрани исходный запрос, рамки, допущения, план текущего раунда, назначенные участки, результаты и следующий шаг. Записи о сдаче участков сохраняй до публикации результата, с номером раунда и ID участка.
2. Создай draft.json по примеру ниже. Выполни python <dashboard.py> publish <каталог>. Команда атомарно обновляет state.json. Запусти python -u <dashboard.py> serve <каталог> в долгоживущем сеансе терминала, сообщи URL из stdout и оставь сервер работать после завершения прогона. Он слушает 127.0.0.1 и выдаёт только шаблон и state.json. Если запуск недоступен, продолжай сохранять состояние и сообщи причину.
3. Обновляй draft.json и выполняй publish при смене этапа, начале раунда, назначении или сдаче участка, регистрации существенных источников и противоречий. До запуска исследователей опубликуй одним снимком списание раунда и его участки с ID, текстом и статусами. В ID участка включай номер раунда, например R1-A1. Перед финальной публикацией запиши report.md.
4. При возобновлении прочитай state.json и notes.md. Перенеси опубликованное состояние в draft.json, прими номер раунда и его план из state.json. Примени сохранённые результаты по ID опубликованных участков. Повтори только незавершённые участки текущего раунда, предварительно проверив доступные результаты уже запущенных исследователей. При необходимости заново запусти дашборд и сообщи URL.

Пример draft.json:

Для вопроса со статусом «Пробел» заполни next_check: коротко укажи, какие поля или наблюдения за какой период позволят продолжить проверку. Дашборд показывает этот текст рядом с открытым вопросом. Если практического способа проверить вопрос нет, укажи ограничение.

Для каждой карточки укажи question_id существующего вопроса и непустой список source_ids из реестра sources. При финальной публикации каждый «Обоснован» должен иметь карточку. Для «Пробел» без установленного результата карточка не требуется. Версия схемы определяется при первой публикации автоматически.

Для каждой существенной находки добавь объект в claims. Поля text, status, effect, evidence, limitation обязательны. В effect укажи размер и базу сравнения либо почему эффект пока неизвестен. В evidence укажи ID источника и результат проверки. Для гипотезы назови в limitation проверку, которая способна её опровергнуть.

Для локального источника добавь строки file (имя файла) и location (лист и ячейки, строки или точное место расчёта). Полный текст итогового report.md публикуется вместе с состоянием и доступен для скачивания с дашборда.

При итоговой публикации добавь в draft.json строку finding с главным выводом из report.md в двух-трёх предложениях. Сохрани период сравнения и существенное ограничение. При частичном исходе укажи, какой вопрос остался открытым. Эта строка открывает итоговый экран.

Перед финальной публикацией проверь покрытие исходного запроса в report.md. Каждому вопросу назначь «Обоснован» или «Пробел». Для незакрытого вопроса объясни последствия и выбери общий статус «Частично». Если расхождение не влияет на ответ, зафиксируй причину в conflicts и отметь «Разобрано». Если влияет и объяснение ещё не найдено, оставь «Открыто» и укажи «Частично».

    {
      "topic": "Тема",
      "phase": "Рамки",
      "status": "В работе",
      "rounds": {"used": 0, "limit": null},
      "questions": [{"id": "Q1", "text": "Вопрос", "status": "Запланирован"}],
      "assignments": [],
      "sources": [],
      "conflicts": []
    }

Статус прогона — «В работе», «Завершено» или «Частично». Статусы вопросов — «Запланирован», «Поиск», «Проверка», «Обоснован», «Пробел». Участок в assignments содержит id, question_id, text, worker и status («Запланирован», «Поиск», «Сдан», «Недоступен»). В одном вопросе может быть несколько участков с разными исполнителями. При публикации автоматически подсчитывается число уникальных субагентов (subagents_count) по полям worker и reviews.*.agent; при повторных запусках можно указать общее целое число в subagents_count явно, чтобы дашборд отражал фактический расход агентов. Для источника используй поля id, title, url, evidence. В evidence запиши ID вопроса, дату, точное место в источнике или основу расчёта, ограничения и связь с общим набором данных. Для локальных источников оставь url пустым, а путь и место укажи в evidence. Для противоречия используй id, text, status («Открыто» или «Разобрано»). В text включи ID расходящихся источников и итог проверки, когда он появится.

Исследователю передай ID и текст участка, период, географию, разрешённые источники и ожидаемый результат. Проси для каждого вывода точное место в источнике, автора, дату, происхождение данных, существенные ограничения и воспроизводимый расчёт, если он нужен. Для спорного вывода запроси альтернативное объяснение или контрдоказательство. Запись общих файлов остаётся у координатора.
